## 1. 办公文档能力总览

Aivory 前端把三类办公文档（PPT / Word / 表格）的能力按「预览」与「编辑」两条线组织，全部跑在浏览器里，后端只当「二进制仓库」。

| 类型 | 预览（只读） | 编辑（可写） | 渲染/编辑库 | 导出 OOXML 的载体 |
|------|------------|------------|------------|------------------|
| **PPT (.pptx)** | `@aiden0z/pptx-renderer/browser`（`pptx-native-preview.tsx`） | ①自研「只改文本」编辑器（`pptx-editor.tsx` + `src/lib/ooxml/pptx.ts`）；②成品可交给 **Docmee 厂商 iframe 编辑器**做整页级编辑（`docmee-editor.ts`） | 渲染 `@aiden0z/pptx-renderer`；编辑文本 `src/lib/ooxml/pptx.ts` | 前端 `archive.build()` 直接产出 `.pptx` Blob |
| **Word (.docx)** | `docx-preview`（`docx-native-preview.tsx`） | `@docx-editor.dev/react` 开源核心（`docx-editor.tsx`），浏览器内无损回写 OOXML | `@docx-editor.dev/react` | 前端 `editor.save()` 产出 `.docx` |
| **表格 (.xlsx)** | 自研解析 + AG Grid 社区版（`spreadsheet-native-preview.tsx`） | 自研：AG Grid 编辑 + 自研 OOXML 写入（`spreadsheet-editor.tsx` + `src/lib/ooxml/xlsx.ts`） | AG Grid + 自研 `src/lib/ooxml` | 前端 `archive.build()` 产出 `.xlsx` |
| **公式求值** | — | 自研安全求值器（`src/lib/ooxml/formula.ts`） | `@formulajs/formulajs`（白名单函数） | — |
| **HTML 预览** | 沙箱 iframe 实时渲染 | — | 内联 `@tailwindcss/browser` | — |

关键工程决策（来自源码注释）：
- **「外科手术式」OOXML 编辑**是核心原则：只改写用户动过的 entry，其余 zip entry 原样透传，保证布局/主题/图表/母版等不被破坏（`src/lib/ooxml/pptx.tsx`、`src/lib/ooxml/xlsx.ts`、`archive.ts`）。
- 不做「重新排版的从零生成」：`pptx-editor.tsx` 明确注释「新增形状/重新布局是 600–1000+ 工程师日的大问题，本项目刻意不做」。

## 2. OOXML 实现深度分析（`src/lib/ooxml/`）

这是四个文件的完整职能，**新后端的 Python（`python-docx`/`python-pptx`/`openpyxl`）只在「需要服务端生成 OOXML」时才需要对标**。

### 2.1 `archive.ts` — ZIP 容器薄层（`src/lib/ooxml/archive.ts`）

自研 `OoxmlArchive` 接口封装 JSZip：

```
archive.ts:15-24  export interface OoxmlArchive {
                    names: string[]; has(name): bool; read(name): Uint8Array;
                    write(name, content): void; build(mimeType): Blob
                  }
```

- `loadOoxmlArchive`（archive.ts:26）解压 xlsx/docx/pptx，返回增删改查句柄。
- **外科手术契约**：从未 `write` 过的 entry 在重建时原样返回（archive.ts:7-9），保证「未动内容逐字节一致」。
- `xmlDeclarationOf/decodeXml/encodeXml`（archive.ts:59-69）：因为 `XMLSerializer` 会丢失 `standalone="yes"`，保留原始 XML 声明、用 UTF-8 编解码。

### 2.2 `xlsx.ts` — 表格的读取/写入（`src/lib/ooxml/xlsx.ts`）

- 命名空间：SpreadsheetML 是**默认命名空间**，因此创建元素必须用 `createElementNS`（xlsx.ts:6-14、204）。
- 引用解析：`columnIndexOf/columnNameOf/splitCellRef`（xlsx.ts:47-70）。
- 解析：`readSharedStrings` 把 `<si>/<t>` 拼成共享串表（xlsx.ts:86）；`resolveSheets` 通过 `workbook.xml` + rels 定位每个 sheet 的路径（xlsx.ts:95）；`parseSheet` 把 `<c>` 单元格（`inlineStr`/`s` 共享串/`b` 布尔/`str`/数字）映射为 `SheetCell{kind,text,formula}`（xlsx.ts:120-169）。
- 写入：`applyCellEdit`（xlsx.ts:189）原地改一个 `<c>`，**保留 `s` 样式索引**；写字符串用 `inlineStr` 避免改动 sharedStrings.xml；`ensureRow/ensureCell`（xlsx.ts:246/260）按行号/列序插入新行列；`markFullRecalc` 写 `<calcPr fullCalcOnLoad="1">` 强制 Excel 重算（xlsx.ts:280）。
- 命名空间注意点（源码明确注释）：SpreadsheetML 用默认命名空间，若用 `createElement` 会产生 `<v xmlns="">` 被 Excel 拒绝，所以全部走 `createElementNS`。

### 2.3 `pptx.ts` — PresentationML 的文本外科编辑（`src/lib/ooxml/pptx.ts`）

- 命名空间是**前缀式**（`p:`/`a:`），且本模块**从不创建元素**，只替换已有文本节点，规避了命名空间问题（pptx.ts:4-13）。
- `resolveSlides`（pptx.ts:61）：通过 `p:sldIdLst` + `_rels/presentation.xml.rels` 解析 `SlideRef[]`（name + 路径）。
- `slideTextElements`（pptx.ts:87）：收集一张 slide 上所有 `<a:t>` 文本节点；`parseSlideText` 取其文本。
- `writeSlideText`（pptx.ts:111）：按 index 数组把 `<a:t>` 替换为编辑文本；带首尾空白时写 `xml:space="preserve"`；返回 `{xml, changed}`。
- 关键：写回的 xml 通过 `xmlDeclarationOf` 保留原始声明 + 行首清理（pptx.ts:129-133）。

### 2.4 `formula.ts` — 安全公式求值（`src/lib/ooxml/formula.ts`）

- **明确不用 `new Function`/`eval`**（formula.ts:4-9）：公式来自用户文件，直接当 JS 执行会跑攻击者代码。用「显式 tokenizer + Pratt 解析器 + 函数白名单」。
- 白名单函数：`ABS AND AVERAGE CONCATENATE COUNT COUNTA IF IFERROR INT LEN MAX MIN MOD NOT OR POWER ROUND SQRT SUM TRIM UPPER`（formula.ts:55-58、`@formulajs/formulajs` 提供）。
- `evaluateFormula`（formula.ts:161）支持数字/字符串/单元格引用/区间/运算符/括号；区间只能作为函数参数（`asScalar` 拒绝裸区间）。
- 超出语法或白名单抛 `FormulaUnsupported`，前端如实展示「不支持」而非显示错数。

### 2.5 `ooxml-archive.ts` — 预览前的安全校验（`src/lib/ooxml-archive.ts`）

- 不为对抗式 OOXML 解压全部内容，先读 ZIP **中央目录元数据**做廉价检查（ooxml-archive.ts:44-48）。
- 限制（ooxml-archive.ts:13-18）：≤4000 entries、单 entry ≤32MB、总 ≤128MB、压缩比 ≤500。
- 拒绝：多盘 ZIP、ZIP64（预览）、加密 entry、超高压缩比（zip 炸弹防护）。

## 3. AI PPT 生成流程

### 3.1 前端自建 UI（`src/pages/ppt/AiPPT.tsx`）

AI PPT 是一个**四步向导**（`AiPPT.tsx:8-13` 顶部注释）：

1. **输入**（`StepInput`，AiPPT.tsx:666）：五种输入类型 `AI_PPT_INPUT_TYPES=[1,6,5,2,7]` = topic/text/url/upload/markdown（`src/lib/aippt-outline.ts:48`）。上传支持 `.docx/.doc/.pdf/.txt/.md/.markdown/.pptx/.ppt`（AiPPT.tsx:752）。
2. **大纲**（`StepOutline`，AiPPT.tsx:902）：通过后端 SSE **流式**输出，前端按 80ms 定时 flush 避免过量重渲染（`pushDelta`，AiPPT.tsx:191）。大纲是 Markdown，`parseAiPPTHeadings`（aippt-outline.ts:22）解析 `#/##/###/####`，并给结构性警告（缺 title/chapters/pages，aippt-outline.ts:74）。
3. **模板**（`StepTemplate` + `TemplatePicker`）：从画廊选模板（类型 1=系统、4=账号自建）。
4. **成品**（`StepResult`，AiPPT.tsx:1075）：预览 `.pptx`（用 `DocumentPreview` 渲染）、下载、重命名、换模板重渲、AI 重写。

另有「我的 PPT」`DeckList` 列出自己名下的 deck 记录。

### 3.2 前端→后端端点（`src/api/endpoints.ts:615` `aipptApi`）

### 3.3 后端（Go）的角色：Docmee V2 代理（`server/internal/api/aippt_client.go`）

- 后端持有 **Docmee Api-Key**，浏览器永远看不到；用 `aipptApi.resourceUrl/editor` 的 token 也由服务端每开一次现发（`docmee-editor.ts:8-10`「token 来自我们的 server，永不触碰 Api-Key」）。
- Docmee V2 客户端要点（aippt_client.go:18-35）：
  - 失败以 **HTTP 200 + 非零 `code` 信封**返回，每次调用必须查 `code` 而非状态行；
  - `generateContent` 流式结束时 status=4 只带大纲树，Markdown 需从 `text` delta 累积；
  - 上游 URL 用 `token` 请求头（非 Authorization）。

`server/internal/api/aippt_handlers.go:24-35` 列出全部 `/api/me/ppt/*` 路由；`meAiPPTGenerateHandler`（aippt_handlers.go:544）负责渲染 + 扣费 + 把生成的 `.pptx` **镜像进用户的 files**（`deck.FileID`）。

### 3.4 Docmee 厂商编辑器（slide 级编辑，`src/lib/docmee-editor.ts`、`docmee-editor-dialog.tsx`）

- 创建用自建 UI，但**整页级 slide 编辑**交给厂商 iframe SDK：`@docmee/sdk-ui@1.6.47`（docmee-editor.ts:15-18，可用 `VITE_AIVORY_DOCMEE_SDK_URL` 覆盖）。
- `createDocmeeEditor`（docmee-editor.ts:116）实例化 `page:'editor'`、`pptId`、`creatorVersion:'v2'`。
- 关闭弹窗时 `syncFile` 调 `refresh-file` 把编辑后的 `.pptx` **拉回并镜像到用户文件**（docmee-editor-dialog.tsx:43-60）。

## 4. 文件上传 / 下载 / 预览链路

### 4.1 文件页（`src/pages/files/UserFiles.tsx`）

- 主从布局：桌面端「文件浏览器 + 预览面板」；小屏「列表 → 预览」。
- 数据源：`authApi.myFiles(...)`（`/me/files`，endpoints.ts:255）分页列目录。
- **选择即预览**：`openPreview`（UserFiles.tsx:208）先按 `file-preview-kind` 检查字节上限，再 `authApi.myFileContentBlob(source,id)`（`/me/files/content?source=file|document&id=`，endpoints.ts:276）拉二进制。
- 删除：`authApi.deleteMyFiles([{source,id}])`（`/me/files/delete`）。
- 另存副本：`authApi.saveDocumentCopy`（`/files` 上传，endpoints.ts:269）——编辑器保存的 Blob 作为新文件入库。
- 下载：`fileContentUrl`（UserFiles.tsx:88）/ `myFileContentBlob` 生成 objectURL + `<a download>`。

### 4.2 预览分发器（`src/components/files/document-preview.tsx`）

`DocumentPreview` 是 Files、聊天附件、admin 库存共享的**无 chrome 预览面**。`documentPreviewKind(name,mime,backendKind)`（`src/lib/file-preview-kind.ts:250`）按扩展名→MIME→后端 kind 三级推断预览类型：

- 图片：`objectURL` 直接 `<img>`。
- PDF：`PdfNativePreview`（基于 pdfjs）。
- `docx`：`DocxNativePreview` — 用 `docx-preview` 渲染（docx-native-preview.tsx:89），先 `validateOoxmlArchive` 防 zip 炸弹（docx-native-preview.tsx:74），渲染树先建在游离 DOM 防过期渲染，再等字体注入稳定（:94-140），并 `sanitizeDocumentLinks` 清洗外链（:31）。
- `pptx`：`PptxNativePreview` — 用 `@aiden0z/pptx-renderer/browser` 的 `PptxViewer` + `parseZipLazyMedia/buildPresentation`（pptx-native-preview.tsx:64-77），含 xppt-security `preservePptxParagraphTextFills`（修渲染器文字颜色被 fontRef 遮蔽）与 `removeExternalPptxResources`（移除会发起网络请求的外部 rels，pptx-security.ts:64）。
- `xlsx`：`SpreadsheetNativePreview`（AG Grid 只读网格，worker 解析行列）。
- `html`：`SandboxedHtmlFrame` 沙箱 iframe **实时**渲染（见 4.3）。
- `text`：`<pre>` 源码。

字节上限：文本/HTML 2MB、Office 20MB、PDF 40MB（file-preview-kind.ts:21-23、381）。

### 4.3 HTML 预览与分享（`src/lib/html-preview-document.ts`、`src/api/html-previews.ts`）

- `buildHtmlPreviewDocument`（html-preview-document.ts:85）：给 AI 产出的 HTML 注入 `@tailwindcss/browser` 运行时；按「是否用了 Tailwind 工具类」决定是否注入（`:48`）；把 Google Fonts 重写为国内镜像（`:64`）避开域名墙。
- htmlPreviewsApi.create（html-previews.ts:12）POST `/html-previews` 存一份公开预览（`buildPublicHtmlPreviewDocument`，:96），返回 `/public/html-previews/:token` 公开 URL —— 用于跟别人分享 AI 生成的可交互页面。

### 4.4 编辑器注册（`src/components/files/editors/`）

`document-editor.tsx:11-18` 是懒加载注册表：`code→codemirror`、`sheet→spreadsheet-editor`、`docx→docx-editor`、`pptx→pptx-editor`。每个编辑器 `onChange({bytes: Blob})` 回传序列化结果、`flushRef` 提供「按需保存」把防抖窗口内的编辑持久化。

- `docx-editor.tsx`：`@docx-editor.dev/react` 核心（Apache-2.0，注释明确 `/pro` 不 ship），`api.save()` 全量序列化（900ms 防抖），i18n 层叠（zh-Hant 叠在 zhCN 上）。
- `spreadsheet-editor.tsx`：AG Grid 编辑 → `writeSheetEdits` 外科写入；公式单遍求值；只写回 dirty 单元格（:197）。
- `pptx-editor.tsx`：把每页 `<a:t>` 变成输入框，`writeSlideText` 打补丁，1s 防抖，补丁后的包喂回渲染器做实时预览（:164）。

## 6. Python 复刻要点

### 6.1 核心洞察：前端保持不动的前提下，Python 后端只需「端点契约对齐 + 文件服务」

办公文档的**生成/编辑/导出逻辑几乎全在前端**：
- PPTX/DOCX/XLSX 的编辑 + 回写是浏览器自研库或第三方编辑器完成；
- AI PPT 的 `.pptx` 由后端调 Docmee 生成后**整文件镜像**（`deck.file_id`）存入用户文件，前端直接用 `/me/files/content` 下载并交给 `@aiden0z/pptx-renderer`/`docx-preview`/AG Grid 渲染；
- 唯一需要后端「生成 OOXML」的场景，是**服务端要用 python-docx/python-pptx/openpyxl 重新实现** Docmee 或对话导出——但这是可选增强，前端已有的生成能力（如 `docx-export.ts` 用 `docx` 包导出 `.docx`）并不依赖后端。

因此 Python 后端的正确姿势是：**做一个与 Go 后端相同的「二进制文件仓库 + 元数据 + 向外提供字节」服务**，不要把 OOXML 生成搬回服务端。

### 6.3 用 Python 重新实现 OOXML 生成：思路与差距

如果确需「服务端生成 OOXML / 给 AI 产物做服务端兜底」，可用 Python 生态对标前端自研库：

| 前端能力 | 前端实现 | Python 对应 | 差距/注意 |
|---------|---------|------------|----------|
| ZIP 容器外科编辑（保留未动 entry） | `src/lib/ooxml/archive.ts`（JSZip） | `zipfile` 不易「改一项重建并原样保留其它项」，需自行读写 central directory 或接受重建带来的字节差异（前端契约是 entry 内容一致，非整包字节一致，见 archive.ts:11-13） | Zip 重建会对未动 entry 也能保持内容一致（只需不重压已读项），可满足前端；Python 用 `zipfile` 解包→改单个 part→重打包，保持其它 part 内容不变即可 |
| SpreadsheetML 解析/写入 | `src/lib/ooxml/xlsx.ts`（`<f>`/`<v>`/`inlineStr`/`calcPr fullCalcOnLoad`） | **`openpyxl`**：读公式用 `cell.value`（公式串）与 `data_only` 文件取缓存值；写公式直接 `cell.value='=SUM(A1:A2)'`；写 `fullCalcOnLoad` 需自行改 `calcPr` 或用 `workbook.calculation.fullCalcOnLoad=True` | openpyxl 默认**重写整个 xlsx 会丢样式外的部分对象**（图表、数据透视、部分格式）——这与前端「只改 dirty 单元格、其它 entry 原样」的保证不同。要等价需用 openpyxl 打开后只设目标单元格再 `save()`，但 openpyxl 仍会重写整表 XML。**推荐：若无强制需求，后端不重写 xlsx，只存前端产物** |
| PresentationML 文本编辑 | `src/lib/ooxml/pptx.ts`（`<a:t>` 替换） | **`python-pptx`**：遍历 `shape.text_frame.paragraphs[i].runs[j].text` 改文本；但 python-pptx **会重建/丢弃它不认识的元素**的风险存在 | python-pptx 能改文本框文本，但同 openpyxl，`save()` 会重写 content types/rels。若要求「前端不改的字节一致」，python-pptx 不保证；**默认应由前端编辑，不走后端** |
| Word 无损编辑 | `@docx-editor.dev/react` + `src/lib/docx-export.ts`（docx 包生成） | **`python-docx`**：生成/追加段落、表格、标题、内联图片、OMML 公式（`mathml2omml`→`ImportedXmlComponent`） | `docx-export.ts` 已完成「Markdown→docx」导出（含 KaTeX→MathML→OMML 公式），说明导出在会话 AI 侧前端已能做；Python 端若要复刻导出可用 `python-docx` + `lxml` 注入 OMML |
| 公式求值 | `src/lib/ooxml/formula.ts`（自研解析器 + `@formulajs` 白名单） | 无直接等价；可用 `formulas`/`pycel`/`schedula`，或用 `formulas` 库 | 前端已有安全求值，后端**不需要**再实现，除非要做服务端公式计算（如表格 AI 计算） |
| OOXML 安全校验（zip 炸弹防护） | `src/lib/ooxml-archive.ts` 中央目录预检 | Python 侧如到服务端解析 OOXML，须复刻：entry 数、单文件/总体解压大小、压缩比上限；Python `zipfile` 需手动校验中央目录（或先用 `zipfile.ZipInfo` 的 `file_size/compress_size/compress_type` 汇总拒绝） | 前端 `docx-native-preview.tsx:74` 已先做校验再喂给解析器，服务端只在「自己解析内容做索引/提取文本」时才需要 |

### 6.4 关键架构建议（Python 复刻）

1. **前端不动**：所有预览/编辑器组件读取的是 `myFileContentBlob` 返回的原始二进制 + `documentPreviewKind` 推断的类型。Python 后端只要保证 `/me/files/content`、`/files/:id`、`/documents/:id/content` 返回正确的字节与 `Content-Type`，前端整套 OOXML 能力零改动即可用。
2. **AI PPT 保持「代理模式」**：Python 后端照搬 Go 的 Docmee V2 客户端语义（信封 `code` 判断、`generateContent` status=4 时从 delta 累积 Markdown、token 放 `token` 请求头、SSE 转成前端 `delta/done/error` 事件、HTTP 402 ↔ `insufficient_credits`）。前端 `docmee-editor.ts`、`docmee-editor-dialog.tsx` 依赖 `/me/ppt/decks/:id/editor` 给出 `{token, ppt_id, sdk_url, domain}`，Python 端照提供即可。
3. **文件镜像链路**：AI PPT 生成/Refresh 后 `deck.file_id` 指向用户文件记录，前端才会显示「已保存」并允许下载/预览。Python 端在 `pptx`/`refresh-file` 处理里要真正把 Docmee 产出的 `.pptx` 落库为文件记录并回填 `file_id`。
4. **html-previews 可作为纯存储**：`html-previews.ts` POST `/api/html-previews` → 存 HTML → `/public/html-previews/:token` 公开读。Python 侧做「保存 + 无鉴权只读」即可，前端负责注入 Tailwind 运行时构建完整文档。
5. **OOXML 生成 API 属可选**：若想「服务端也能生成 docx/pptx/xlsx」（例如把某个 AI 产物落盘），用 `python-docx` / `python-pptx` / `openpyxl` 可行，但要清醒：**这三者重新保存会重写整包，不能保证「前端未动内容逐字节一致」**——这与前端自研库的外科手术契约不同。最稳妥的复刻策略是**永远优先存储/透传前端已生成好的 OOXML Blob**，服务端生成仅作兜底/新能力，不作为主链路。

# Aivory 整体架构与技术栈调研

> 本文档是 Aivory 项目复刻调研的**入口与索引**。目标读者是需要复刻本项目（特别关注把 Go 后端替换为 Python 后端）的工程师。
> 版本基准：`v2.5.2-beta.12`，分支 `main`。

---

## 1. 项目定位

Aivory 是一个 **自托管的 AI 工作台（Self-hosted AI Workspace）**，把以下能力整合到一个产品中：

- **对话（Conversations）**：接多家 AI 模型（Provider/Channel 机制），多会话、分支、流式回复、实时思考过程。
- **研究与创作（Research & Creation）**：联网搜索、网页/文档阅读、生成代码/图片/报告/表格/PPT/办公文档并可导出下载。
- **知识库（Knowledge / RAG）**：从团队文档构建向量库，对话中检索并引用来源。
- **个人/团队工作区（Workspaces）**：权限隔离、邀请成员、共享项目/会话/文件/知识。
- **管理后台（Admin）**：配置 AI 服务（Channels/Models）、成员管理、套餐与用量限制、审计与成本、备份恢复、系统升级。
- **办公套件**：内嵌 Word（`.docx`）、PPT（`.pptx`）、Excel（`.xlsx`）在线编辑与 AI 生成（AI PPT）。

### 部署形态
- **Full（团队版）**：PostgreSQL + Redis + Qdrant + 多容器。
- **Personal（个人版）**：SQLite 单库，内嵌向量，minimal 容器。
- **Desktop**：Electron 桌面客户端（Windows/macOS/Linux），自带本地 server 与离线下发。

### 仓库顶层布局
```
Aivory/
├── src/               前端 Web 应用（React + TypeScript + Vite）
├── server/            Go 后端 API 服务（含 migrations）
├── sandbox-service/   Python 代码执行沙箱（独立服务）
├── desktop/           Electron 桌面壳（本地 server + 窗口 + 更新）
├── deploy/            生产/个人部署的 Docker Compose
├── updater/           桌面客户端更新器
├── tests/             浏览器 e2e、前端单测、沙箱单测脚本
└── docs/              设计/配置参考/产品文档
```

## 3. 端到端请求链路（一次聊天请求）

```
浏览器 (React)
   │  POST /api/conversations/:id/messages   (含历史、附件、生成配置)
   ▼
Go HTTP Router (internal/api/router.go)
   │  middleware: 认证JWT → 限流 → CORS → 请求日志
   ▼
messages_handlers.go
   │  store: 持久化用户消息
   ▼
llm.Orchestrator (internal/llm/orchestrator*.go)
   │  组装消息 → 调用 llm.Registry 选 Provider → 若需则调用 Tools
   ├─→ 工具：tools.Registry (搜索/网页/代码/文件/PPT/...)
   ├─→ RAG：rag.Service (向量检索，注入知识库上下文 + 引用)
   └─→ Sandbox：python 沙箱 (执行代码)
   │  逐 token 生成
   ▼
SSE 流 (internal/sse + msgcache)
   │  progress / reasoning / tool_logs / delta / done
   ▼
浏览器实时渲染（渐进式输出 + 回复动画 + 对话分支导航）
```

**关键点**：后端是**有状态编排 + 服务端推送**模型，而非简单的「请求-转发」。复刻时 Python 端要重点复刻 `Orchestrator` 的编排状态机与 SSE 协议。

## 5. 核心领域模型（数据库）

由 `server/migrations/*.sql` 与 `internal/store` 定义。核心表（概要）：

- **用户与租户**：`users`、`workspaces`、`workspace_members`、`roles`

- **对话**：`conversations`、`messages`、`message_branches`、`generation_configs`、`conversation_shares`
- **文件/制品**：`files`、`artifacts`、`documents`
- **知识库**：`kbs`、`kb_documents`、`chunks`（向量）、`kb_documents_chunks`
- **管理/计费**：`settings`、`channels`、`models`、`plans`、`subscriptions`、`credit_packages`、`payments`、`usage_records`
- **工具/审计**：`tool_logs`、`audit_logs`、`notifications`、`announcements`

## 6. 启动装配流程（server/cmd/api/main.go）

`main.go` 是整个后端唯一的启动入口，展现依赖装配顺序（§ 对应 `design.md` / 注释）：

```
config.Load()                  → 读取环境变量（.env）
config.Validate()              → 生产态禁止 dev JWT_SECRET
store.Open(DB URL)             → 打开 PG 或 SQLite
store.Migrate()                → 启动时自动迁移
store.Seed()                   → 播种初始 admin 用户
cache: Redis(有 URL) / Memory(无)  → 缓存+PubSub
   └ goroutine 订阅 "cfg:invalidate" → 配置变更广播
queue.NewInProcess()           → 进程内异步队列
auth.New()                     → JWT service
llm.NewRegistry()              → Provider 注册表
rag.New() + SetExternalConfig  → RAG 服务（嵌入/向量）
vector: Qdrant / SQLite/Disabled
rag: asynq(Redis) / in-process
tools.NewRegistry(db,cfg)      → 工具注册表（含 sandbox 客户端）
Orchestrator(db, providers, tools, rag, cache, queue, taskLLM, memoryWorker)
pdfexport.New()                → PDF 渲染
api.NewRouter(Deps{...})       → 装配全部 handler
http.Server{ WriteTimeout: 90min }  ← SSE 长连接需要
goroutine: archive GC（归档清理）、ingest recovery、resource cleanup
graceful shutdown (SIGINT/SIGTERM)
```

**复刻提示**：Go 用「构造一个 `Deps` 结构体 + 显式装配」完成依赖注入，无框架容器。Python 复刻可用 FastAPI `lifespan` + 显式 service 装配，或轻量 DI。

## 7. 关键横切设计决策（复刻必须理解）

1. **单一可执行**：一个 `main.go` 进程承担 HTTP + 队列 worker + 后台 goroutine（GC/恢复）。Python 端需决定单进程（FastAPI + 内部 worker 线程/`asyncio` task）还是分进程（如 Celery/sarps）。
2. **SSE 长连接**：`http.Server.WriteTimeout = 90min`，IDLE timeout 20min（照顾反向代理 keep-alive）。Python（uvicorn/gunicorn + FastAPI `StreamingResponse`）需对应设置。
3. **PG/SQLite 双后端**：`store/pgcompat` 抹平差异。个人版跑 SQLite，生产跑 PG。Python 可用 SQLAlchemy 抽象，但要注意本项目用**手写 SQL + 兼容层**而非 ORM。
4. **Redis 可选**：无 Redis 时降级为进程内 cache/queue（dev/个人）。这让个人部署零依赖。Python 复刻若不想依赖 Celery+Redis，可先做进程内队列。
5. **配置全部环境变量**：`internal/config`/`envcfg`，`docs/config-reference.md` 有清单。
6. **安全纵深**：限流（IP 粒度 × 每接口）、验证码（滑块拼图）、出站安全（SSRF 防护 `netsafe`）、上传文件 guard（`fileguard`）、生产 JWT 守卫。
7. **可插拔 Provider**：`llm.Registry` 支持任意 OpenAI 兼容 API + 专用适配。频道（Channel）与模型（Model）分离管理。

## 9. 复刻总体建议（先读）

- **后端语言替换为 Python**：主要用 **FastAPI**（异步、类型、依赖注入）承担 HTTP 层 + SSE；用 **SQLAlchemy 2.0 (async)** 或 **SQLModel** 承担存储层；JSON 结构化 LLM 调用可用 **Pydantic**（与现有 `typesafe`/`TaskLLM` 对齐）。
- **保留 Python 沙箱**：`sandbox-service` 本身就是 Python，可直接复用其协议与 Dockerfile，极大降低返工。
- **前端几乎完全复用**：后端是「服务端驱动的同一套 HTTP/SSE 协议」，只要协议兼容，React 前端无需改写即可复用。**这是复刻的最大红利** —— 优先保证 API 端点、请求/响应 JSON、SSE 事件结构与原 Go 后端一致。
- **复杂度集中点**：LLM 编排（流式 + 工具循环 + 记忆 + 上下文压缩）、RAG 摄取流水线、PG/SQLite 双后端。复刻时先做「聊天 + 认证 + 存库」最小闭环，再逐步加工具/RAG/办公/支付。

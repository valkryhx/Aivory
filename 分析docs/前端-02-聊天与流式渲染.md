## 2. SSE 流式消费实现（核心）

### 2.1 客户端传输（`src/api/client.ts`）
生成流用 **fetch + ReadableStream**（非 EventSource），因为需要 POST 请求体与自定义签名头：

- `streamSSE(path, body, signal)`（client.ts:494）：`fetch`、`credentials:'include'`、`accept:'text/event-stream'`，带请求签名头；按 `\n\n` 切分帧，解析 `id:`/`event:`/`data:`，`data` 尽量 `JSON.parse`，`yield {event, data, id}`。**POST 创建流不自动重试**（重发会二次生成）。
- `streamSSEGet(path, signal, lastEventId, opts)`（client.ts:575）：`GET` 事件流（如 `/api/events`），**指数退避自动重连**（1s×2^(n-1)，最多 3 次），携带 `Last-Event-ID`，读到 `data.type==='done'|'error'` 结束。

### 2.2 消息发送与消费（`src/store/conversations.ts`）

`sendMessage`（conversations.ts:2009+）向 **`POST /conversations/:id/messages`** 发送：

```ts
{
  text, generation_id,
  kb_ids,              // 本轮启用的知识库
  model_id,            // fast 时省略（隐藏的快速模型）
  parent_id,           // 分支父消息
  branch,              // 是否为分支编辑
  edited_message_id,
  mode,                // 'deep-research' 等
  verify,              // 二次审计
  tool_mode,           // 工具策略
  selected_user_skill_ids, disabled_model_skill_ids,
  selected_tool_ids, web_search, fast,
  attachments: Attachment[],   // 附件
  params,              // 生成参数
  image_style_id, optimize_image_prompt, image_edit,
  locale,              // UI 语言→锚定回复语言
}
```

然后 `for await (const frame of streamSSE(path, body, transportAbort.signal))` 消费流（conversations.ts:2128）。`AbortController` 存入 `streamControllers` Map（conversations.ts:419），供「停止生成」用。

### 2.3 事件协议（前端消费清单）

每个 `frame.data` 是一个 `ApiSseEvent`，按 `ev.type` 分派（列举见 conversations.ts:2168-2400）：

| 事件 type | 前端行为 | 关键字段 |
|---|---|---|
| `message_start` | **重键**：临时消息 id 换成后端 `message_id`，刷新控制器别名，标记会话非草稿 | `message_id` |
| `text_delta` | 追加到消息 `content`（渐进渲染） | `text` |
| `thinking_delta` | 追加到 `reasoning` 轨迹（实时推理） | `text` |
| `image_status` | 绘图阶段专用 UI | `status: 'optimizing'\|'generating'` |
| `artifact` | 产物出现（代码/HTML/图片/文件），加入列表 | `id/title/url/summary/source` |
| `refusal` | 模型拒绝回答 | `message` |
| `rag` | RAG 检索生命周期行（searching/found/partial/no_hit/error） | `status` 等 |
| `research_plan/task/source/note/phase` | 深度研究进度 | `research` 结构 |
| `verify_started/finding/done` | 二次审计轨迹 | `verify` 结构 |
| `tool_start` | 工具开始；预工具叙述 flush 成推理步骤 | `id/name/input` |
| `tool_input` | 工具入参（`partial_json` 累积解析显示查询/代码成形过程） | `id/input/partial_json` |
| `tool_result` | 工具结果回填进推理轨迹 | `id/...` |
| `done` | **流正常结束**：清理状态 | — |
| `error` | 流异常结束，展示错误 | `error` |

> 这是**前端依赖的生成事件协议**，后端必须准确发送这些 `type` 及其字段（详见《后端-02》的 SseEvent 定义）。

## 3. 对话分支 / 导航

分支在 `conversations.ts` 深度实现（§4.15）：

- **触发**：编辑一条非最新消息 → 通过 `sendMessage({ branch: true, edited_message_id, parent_id })` 开新分支，而非追加到活动叶子。
- **分支树**：`branchPathFromTree`（conversations.ts:525）根据 `branchCount/siblings` 计算当前选中路径与兄弟分支。内存里维护 `branchSwitchTails` / `branchSwitchRevisions` / `branchSwitchConfirmedPaths` 三个 Map（conversations.ts:448-450）处理分支切换的并发与确认。
- **切换时行为**：切换分支会 `abort` 旧分支正在跑的流（`haltBranchStreams` 逻辑，conversations.ts:846），但**不打断仍在运行的兄弟分支**（R4 规则，conversations.ts:1364-1371）——离线流继续跑，重开该分支时被拾起。
- **UI**：`message-row.tsx` 上的分支选择器在消息有多个变体时出现，展示分支数量与切换。

**对后端影响**：`parent_id` + `branch` + `edited_message_id` 的语义是后端的硬契约；快取/持久化消息树（`conversations.ts:441` 预取）依赖后端返回一致的消息树结构。

## 4. 生成控制

### 4.1 停止生成
- `abortStream(assistantMessageId)`（conversations.ts 定义于 414，实现 647+）：通过 `streamControllers` Map 找到 `AbortController` 并 `abort()`，中断本地 POST 读取器；同时请求后端 **`POST /conversations/:id/stop`**（`message_id` 指定停止目标，conversations.ts:2199 调用 `conversationsApi.stop`）让服务端停止生成并持久化已产出的部分。
- `ChatThread.tsx` 的 `stopAll()`（:395）停止当前可见分支最新一条仍在流的消息；composer 通过 `onStop`（:816）接入手动停止按钮。

### 4.2 重新生成 / 编辑重发
- **重新生成**：对某条 assistant 消息发起 `regenerate`，同样走 `streamSSE`，用独立控制器（`'-regen'` 别名，conversations.ts:859）。
- **编辑重发**：修改用户问题 → 若在非叶子位置则开新分支（见第 3 节）。
- **排队轮次**：`queued-turns.ts` / `queued-turn-dispatcher.tsx` 管理等待的轮次（在多轮时排队）。

## 5. 渐进渲染与实时推理

- **text_delta 追加**：每个 `text_delta` 直接拼接进 `content`（conversations.ts:2204-2208），浏览器随流渐进渲染。
- **thinking_delta → reasoning 轨迹**：`appendThinkingDelta` 把思考片段追加进有序的推理轨迹（`reasoning`），`reasoning-trace.tsx` 渲染，`reasoning-preview.ts` 处理折叠/展开，支持**逐片段/逐字动画**（`reasoning-trace.module.css`）。
- **reply-wait-animation**：`reply-wait-animation.tsx` 在等待首个 `message_start`/首 delta 前展示动画回复等待反馈（替代无信息量 loading，遵循 PRODUCT.md 设计原则）。
- **工具叙述**：模型在工具调用前的自然语言叙述会被 `flushNarration` 归入「推理步骤」，保证最终答案只含工具后的正文（conversations.ts:2295）。
- **image_status**：绘图阶段展示专用「生成中」占位 UI，`artifact` 到达后替换（conversations.ts:2225）。

## 6.「与 Python 后端复刻的接口约定」

前端聊天对后端聊天的**硬性依赖**（新后端必须实现，前端零改动）：

1. **发送**：`POST /api/conversations/:id/messages`，请求体字段见 2.2；响应为 `text/event-stream`。
2. **生成流事件**：`message_start` 必须最先返回并带 `message_id`（前端重键依赖）；随后 `text_delta`/`thinking_delta`/`tool_start`/`tool_input`/`tool_result`/`artifact`/`rag`/`research_*`/`verify_*`；结尾 `done`（正常）或 `error`。字段名与上表逐字一致。
3. **停止**：`POST /api/conversations/:id/stop`（body/query 带 `message_id`）返回后停止生成并持久化部分输出。
4. **重生成/分支**：`parent_id`、`branch`、`edited_message_id` 语义正确；消息树接口返回分支结构（siblings/branchCount）。
5. **实时事件流**：`GET /api/events` 长连接，支持 `Last-Event-ID` 断点续传，`done/error` 结束，用于跨设备同步与通知。
6. **SSE 帧格式**：`event:`/`data:` 两字段，帧以 `\n\n` 分隔，`data` 为 JSON。
7. **鉴权/签名**：与《前端-01》一致（Bearer + 请求签名 + cookie 刷新）。

> 建议用仓库 `tests/browser/run-*.mjs` 的 Playwright 场景对新后端做聊天冒烟：发送、流式增量、停止、分支、重生成逐一验证。

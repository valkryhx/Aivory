# Aivory 多用户写 / 删除操作隔离分析

> 场景：Aivory 是**多用户自托管 AI 工作台**，用户可以用 **Agent（工具）执行写文件、建/删会话、上传删除文件、删知识库、删技能、删项目、删工作区**等「危险操作」。
> 本文档回答：**用户 A 能否用 Agent 删除/覆盖用户 B 的内容？跨用户/跨工作区的写与删除如何被拦住？哪些删除是 owner-only、哪些是 workspace 成员可删、哪些只允许 admin？以及 Agent 写的文件如何保证不越权落到别人的空间？**
>
> 源码基准：Aivory v2.5.2-beta.12（Go 后端）。配套：《agent-subagent流程与多用户隔离分析》《停止生成跨实例精准送达机制分析》《99-复刻路线图-Python后端》《后端-05-数据模型与存储层》。

## 0. 一句话结论（先给答案）

1. **支持**「用户用 Agent 执行写与删除操作」。Agent（deep_research / 工具派发）能写文件（沙箱 `/workspace`）、调用删除类工具，但这些操作**不是无授权执行的** —— 每一层都过**授权闸门**。
2. **多用户内容隔离**由 **四层纵深** 保证，缺一不可：
   - **① 身份层**：JWT claims → `u.ID`（`requireAuth`）。
   - **② 权限层**：权限位（`AllowConversationDeletion`/`AllowWorkspaceDeletion`）+ 用户组 policy + workspace 成员能力位（`CanManage`）三级权限检查。
   - **③ 所有权层（最关键）**：`store` 层所有删除/写入函数**强制带 `u.ID` 参数**做 `WHERE ... AND user_id=?`(或 workspace capability predicate) 过滤 —— **即使拿到别人 id，删除也无操作 / 返回 404**。
   - **④ 资源归属层（物理层）**：文件/沙箱写入全部**绑定 `user_id` + `conversation_id`**；沙箱每个会话是**独立容器 + 独立 `/workspace`**（`archiveKey=conversationID`）；Go 物理写盘走 `fileguard`（防 **路径穿越 / 符号链接逃逸 / 跨进程竞争**）。
3. **不会误删他人内容**：因为「删哪一行」由带 `u.ID` 的 SQL **原子决定**，且「是否允许删这一类」由权限位**先决**；workspace 共享资源再多加一层**作者/管理员**校验（普通成员只能删自己的回合）。
4. **workspace 是例外中的关键**：个人资源（私有会话/文件/技能）**只 owner 可删**；工作区共享资源**owner 或 admin（manager 能力）可删**，普通成员**只能删自己创建的那部分**（消息回合、自己的文件）。

## 1. 危险操作全景：Agent 能写/删什么

| Agent/用户操作 | 写 or 删 | 归属判定（谁来授权） | 核心闸门 |
|---|---|---|---|
| 会话 `DELETE /conversations/:id` | 删 | owner / workspace manager | `permissions.AllowConversationDeletion` + `DeleteConversationWithState(id, u.ID)` |
| 清空全部会话 | 删 | owner（仅个人空间） | `PersonalConversationIDsForDeletion(u.ID)` —— 故意排除 workspace |
| 消息回合 `DELETE .../messages/:msgId` | 删 | owner；workspace 内限**回合作者/会话创建者** | `GetConversation(convID, u.ID)` + workspace author 校验 + `DeleteRound` |
| 上传文件 | **写** | owner（`files.user_id`） | fileguard `PrepareWrite` + `GetFile(id, u.ID)` |
| 删除我的文件 `DELETE /files`（批量） | 删 | owner | `ownsAdminFileRow` + `GetFile(id, u.ID)` + `DeleteStandaloneFileForUser(id, u.ID)` |
| 删除知识库文档 | 删 | KB 有访问权 + 文档 owner | `requireKnowledgeBaseAccess` + `GetDocumentForUser(docID, u.ID)` |
| 删除我的技能 | 删 | owner / （workspace 内 manager） | `GetUserSkillScoped(id, ownerID, workspaceID)` + `current.CanManage` + 用户组 policy |
| 删除项目 | 删 | owner / manager | `GetProject(id, u.ID)` + `CanManageProject` |
| 删除工作区 | 删 | **仅 owner** | `ws.OwnerID == u.ID` + `AllowWorkspaceDeletion` |
| 沙箱执行代码 + 写文件 | **写** | **每会话独立容器/`/workspace`** | `NewSession(archiveKey=conversationID)` + `/workspace` 隔离 + `ResetInputs` |
| 物理文件落盘 | **写** | 路径受根目录约束 | `fileguard.ResolveExisting / PrepareWrite`（防穿越/防 symlink 逃逸）|

> **共性**：任何一个危险操作都是 **「授权检查（能否做这一类）」+「带 `u.ID` 的归属过滤（能否动这一行）」** 双重把关。第二部分是「不误删他人」的根本。

## 2. 删除操作的全部所有权校验（源码逐条）

### 2.1 会话删除：权限位 + owner/workspace manager 双查

`conversations_handlers.go:854` `deleteConversationHandler` 与 `store.DeleteConversationWithState`（`store/conversations.go:837`）：

```go
func deleteConversationHandler(d Deps, w http.ResponseWriter, r *http.Request) {
    u := authUser(r)
    id := pathParam(r, "id")
    // draft 分支走 owner-only 的 DeleteConversationDraftWithState(id, u.ID)
    permissions, _ := requestPermissions(d, r)
    if permissionErr != nil || !permissions.AllowConversationDeletion {
        writeError(w, http.StatusForbidden, errForbidden); return   // ← ① 权限位
    }
    deletion, err := store.DeleteConversationWithState(r.Context(), d.DB, id, u.ID) // ← ② 带 u.ID
    if err != nil { writeError(w, 404, errNotFound); return }
    finishConversationDeletion(...)
}
```

`DeleteConversationWithState(ctx, db, id, userID)` 的事务内（`store/conversations.go:844-903`）做**三重 SQL 校验**：

```sql
-- 1) 先取 owner 与 workspace（缺失→ErrNotFound→404）
SELECT user_id, COALESCE(workspace_id,'') FROM conversations WHERE id=?

-- 2) 行锁 + 成员锁（lockWorkspaceMembershipTx），保证「授权决策在提交前不变」
--    （防止并发降权限时留下陈旧的高权限删除判定）
UPDATE conversations SET id=id WHERE id=?            -- 行锁
-- workspace 资源必须能通过 manager 谓词 + 删除能力谓词
SELECT 1 FROM conversations
 WHERE id=? AND workspaceResourceManagerPredicate("conversations")
   AND workspaceConversationDeletionCapabilityPredicate("conversations")

-- 3) 判定"你是否 creator / workspace admin(manager)"
creator := ownerID == userID   // owner 可删整棵内联子树
// workspace admin 可删他人会话（Manager 能力）——见下
```

**关键**：即使 `userID` 传了别人，第 2 步的 `workspaceResourceManagerPredicate`/`capabilityPredicate` 会因为「你不是 owner 也不是 manager」而 `ErrNotFound → 404`，**不会无操作地默默跳过** —— 既防误删也防越权。

### 2.2 清空全部会话：只用「属于自己」的 id

`conversations_handlers.go:894` `clearAllConversationsHandler`：

```go
ids, err := store.PersonalConversationIDsForDeletion(r.Context(), d.DB, u.ID, batch)
// ← 只返回「用户个人空间」的会话，工作区共享会话被故意排除
deletion, err := store.DeleteConversationWithState(ctx, d.DB, id, u.ID)
if errors.Is(err, store.ErrNotFound) { continue } // 并发已删，跳过
```

- `PersonalConversationIDsForDeletion(u.ID)`（`store`）SQL 只取 `user_id=? AND (workspace_id IS NULL OR workspace_id='')` 的**个人私有**会话。
- **结论**：清空自己会话**永远碰不到**工作区共享内容 —— 从"取 id"这一层就把 workspace 隔离了。

### 2.3 消息回合删除：owner + workspace「作者/创建者」限制

`messages_handlers.go:2425` `deleteMessageHandler`：

```go
conv, err := store.GetConversation(r.Context(), d.DB, convID, u.ID) // ← 会话归属
// §workspaces：共享会话里删回合，仅限「该回合作者」或「会话创建者」
if conv.WorkspaceID != "" && conv.UserID != u.ID {
    // 解析该回合的 USER turn（点答案隐含其问题），检查其 author
    author := m.AuthorID
    if m.Role != "user" && m.ParentID != "" { author = 父消息的作者 }
    if author == "" || author != u.ID { writeError(w, 404, errNotFound); return }
}
newLeaf, err := store.DeleteRound(r.Context(), d.DB, convID, u.ID, msgID)
```

- 个人会话：`GetConversation(convID, u.ID)` 已保证归属。
- **工作区共享会话**：额外限制 —— **普通成员只能删「自己写的那个回合」**，不能删别人的回答；会话创建者例外。这就是「共享 ≠ 互删」的具体实现。

### 2.5 知识库文档删除：KB 访问权 + 文档 owner

`kbs_handlers.go:765` `deleteKBDocHandler`：

```go
if !requireKnowledgeBaseAccess(d, w, r, id, false) { return }               // KB 访问权（读）
if _, err := store.GetStandaloneKB(ctx, d.DB, id, u.ID); err != nil { 404 } // KB 归属
```

### 2.6 技能删除：owner + workspace 能力位 + 用户组 policy

`library_handlers.go:608` `deleteMySkillHandler`：

```go
ownerID := authUser(r).ID
workspaceID := libraryWorkspaceID(r)
if !authorizeLibraryWorkspaceCapability(d, w, r, workspaceID, libraryCapabilitySkill, false) { return }
```

- 私有技能还受**用户组 policy**（`UserSkillPolicyAllows`）约束 —— 即使你是 owner，若当前用户组禁止删该类技能也 403。

`workspaces_handlers.go:679` `deleteWorkspaceHandler` —— **仅 owner**：

```go

if err != nil || ws.OwnerID != u.ID { writeError(w, 404, errNotFound); return } // ← owner-only
```

## 3. 写操作的隔离：Agent 写文件为什么不会越权

Agent 的「写」分两条路径，都做了空间隔离：

### 3.1 沙箱执行 / 写文件：每会话独立容器 + 独立 `/workspace`

- Go 侧 `sandbox.Service`（`internal/sandbox/sandbox.go:125-159`）：`NewSession(ctx, archiveKey)`，`archiveKey` 是**稳定键 = conversationID**，`/workspace` 归档/恢复都按此键，**一个会话一个容器/一个工作区**。
- Python 沙箱 `app.py`（《沙箱服务-Python实现》）：`WORKSPACE="/workspace"`，每次 `create` 生成**全新 session**；`STORAGE_DEFAULT_PREFIX="workspaces/"`，工作区 tarball 按会话 id 归档（`app.py:512`）。
- 输入隔离：`ResetInputs(sessionID)` 只清当前会话的 `/workspace/uploads` 与 `/workspace/skills`（`app.py:896-899`），**不碰其它会话**。
- 写路径归一化：`app.py:1003` 把目标路径**归一化到 /workspace 下，拒绝穿越**（`"Normalise the destination to live under /workspace; reject traversal"`）。

→ **A 的代码跑在 A 的容器里，只写 A 的 `/workspace`；即使拿到 B 的 sandbox_id，B 的容器/文件与 A 完全隔离（容器级）。**

### 3.2 Go 物理落盘：`fileguard`（防穿越 / 防 symlink 逃逸 / 防竞争）

所有写到 `UploadDir/ArtifactDir` 的路径都先过 `fileguard`（`internal/fileguard/fileguard.go`）：

- `ResolveExisting(root, path)`（`:59`）：解析真实路径，**拒绝符号链接逃出 root**（`fileguard_test.go` `TestResolveExistingConfinesRealPath`）。
- `PrepareWrite(root, path)`（`:106`）：逐级创建目录，**任何一级是 symlink 或非目录 → `ErrOutsideRoot`**；目标若是 symlink/非常规文件也拒绝（`write_new.go WriteNewFile`）。
- 用法点：`files_handlers.go:781/872`（下载/预览）、`storage_cleanup.go:87`、`rag.go:421/632`（RAG 文档）、`orchestrator_automation.go:737`。
- `storage_lock.go`：跨进程 `LockStorage`（`flock`/Windows 锁）保证**同一存储区不被并发备份/恢复/写互相覆盖**（`admin_backup_handlers.go:548/687`）。

→ **即使 Agent 想写 `../../etc/passwd` 或把 `UploadDir` 软链到别的目录，`fileguard` 在根目录层面就拦截。**

### 3.3 归属写入：每条 files/artifacts 记录都绑 user

- `files` 表带 `user_id`（`idx_files_user`）+ `conversation_id`；`artifacts` 同理。
- 上传：`store.CreateFile(...)` 带 `u.ID`；RAG 引用 `d.StoragePath` + `s.uploadDir` 每次都 `ResolveExisting` 校验。
- Agent 生成的文件（office/artifact）最终 `StoragePath` 落在 `UploadDir`/`ArtifactDir`，其 DB 记录的 `user_id` 是 `RunOpts.UserID`（贯穿身份，见《agent-subagent》§7）。

## 4. 纵横：为什么「危险操作不误删他人」

把四层叠起来，用一个「恶意/偶然尝试」矩阵说明：

```mermaid
flowchart TD
    A[用户/Agent 发起危险操作<br/>删/写某 id] --> B{权限位 / policy<br/>Allow*: 能否做这一类?}
    B -- 否 --> X[403 Forbidden]
    B -- 是 --> C{归属过滤 带 u.ID<br/>GetX(id, u.ID) / DeleteX(id, u.ID)}
    C -- 查不到/不匹配 --> Y[404 Not Found<br/>不产生任何变更]
    C -- 命中本人 --> D{workspace 共享?}
    D -- 否(个人资源) --> E[owner 执行<br/>删本人/写本人]
    D -- 是(KB/会话/项目/技能) --> F{CanManage / 组长/作者?}
    F -- 普通成员 --> G[仅删/改自己那份<br/>共享会话回合仅作者可删]
    F -- owner / manager --> H[按 capability 删整棵]
    note1[物理写盘另经 fileguard<br/>防穿越+symlink逃逸+跨进程锁]
```

**结论**：要「误删/越权删」他人内容，必须同时突破 **权限位 + 带 `u.ID` 的 SQL 归属 + workspace 能力位/作者校验 + fileguard 物理边界** 四关 —— 任一关失败都会使操作**无副作用地终止（404/403）**，而不是「删了个错的东西」。

## 5. 个人 / 工作区 / 管理员的删除语义对照

| 资源 | 用户私有（个人空间） | 工作区共享 | 管理员（admin/owner） |
|---|---|---|---|
| 会话 | owner 可删 | owner 或 workspace manager（经理能力） | 同 owner |
| 消息回合 | owner 可删 | **仅回合作者 / 会话创建者** | 同会话创建者 |
| 文件 / artifact | owner 可删 | owner（文件按 user 归属）| 同 owner |
| 知识库文档 | KB 访问权 + 文档 owner | 文档 owner + KB 访问权 | 依 KB 权限 |
| 技能 | owner + 用户组 policy | owner + workspace `CanManage` | 依 skill 权限 |
| 项目 | owner / `CanManageProject` | 同 | 同 |
| 工作区 | — | **仅 `ws.OwnerID`（owner）** | owner |

> 一句话记忆：**个人资源=私有，仅 owner；工作区资源=共享但分权（owner/manager 全权，成员只能动自己那份）；工作区本身=仅 owner 可删。**

## 6. 对「Python 后端复刻」的实现要点

1. **授权三步不能省**（对应 §1）：每个删/写 handler 依次做 —— `get_permissions()`（权限位）→ `get_xxx(id, user_id)`（归属过滤，查不到即 404，**绝不无操作跳过**）→ 若 workspace 资源再加 `can_manage`/作者校验。**用 FastAPI `Depends` 做权限依赖**。
2. **删除函数签名强制带 `user_id`**：杜绝「按裸 id 删」的隐患。SQLAlchemy 里用 `delete(...).where(Table.id==id, Table.user_id==user_id)`，返回 `rowcount==0` 视为 404。
3. **`workspace_resource` 谓词照搬**：把 `workspaceResourceManagerPredicate`/`workspaceConversationDeletionCapabilityPredicate`/`GetXScoped(id, user_id, workspace_id)` 的复合键语义（user+workspace）移植成 SQLAlchemy `and_(...)`。
4. **清空个人会话只用本人 id 集**：`PersonalConversationIDsForDeletion(user_id)` 加 `(workspace_id IS NULL OR workspace_id='')` 条件。
5. **共享会话回合删除限作者**：删除前解析该回合 USER turn 的 `author_id`，与当前用户比对，不等则 404（对齐 `deleteMessageHandler` 的 workspace 分支）。
6. **文件路径安全**：用 `pathlib.Path.resolve()` + 前缀校验实现 `fileguard.ResolveExisting`/`PrepareWrite`（拒绝 symlink 逃逸与 `..` 穿越）；用 `fcntl.flock`（Unix）/`msvcrt.locking`（Windows）实现 `storage_lock` 跨进程互斥。
7. **沙箱容器隔离是物理底线**：每个会话独立容器 + 独立 `/workspace`（键=`conversation_id`），`reset_inputs` 只清当前会话；`/workspace` 内写路径归一化拒绝 `..`。**Python 复刻时用 `docker` API 每会话一容器即可，复用现有 `sandbox-service`。**
8. **归属字段不能删**：`files/artifacts` 表保留 `user_id`/`conversation_id` 及索引；Agent 生成文件写入时以 `RunOpts.user_id` 记账归属。
9. **事务锁保证授权不陈旧**：`DeleteConversationWithState` 先取 owner→加成员锁→再校验 manager——复刻时用 `SELECT ... FOR UPDATE` + 成员表行锁，防止并发角色降级导致的高权限删除。
